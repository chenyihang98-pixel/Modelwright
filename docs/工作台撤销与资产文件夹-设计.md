# 工作台撤销（Ctrl+Z）与资产文件夹 — 设计（2026-10-26 调研稿）

> 本文是私有源码库里同名设计文档的公开版：内容相同，去掉了本机路径和内部审计 / 实验文件的位置。文中的源码文件名指私有仓库里的位置。

用户 2026-10-26 提出两件事：① 工作台类操作要有 Ctrl+Z 撤销，页面级回退对这种操作不好用，可以学 Unity 的逻辑；② 资产库全是平铺，希望能建文件夹（例：「大肥鱼」，图标用上传的那张图，相关资产都放进去），第一个固定一个「通用资产」，增删改名都在资产总览界面的「⋯」里完成。用户只陈述了愿望，要求以此为基础调研并完善。

本文回答三件事：这两条有没有道理（有，而且互不冲突）；现有代码里它们各落在哪；完善后的规则、数据与接口、测试、不做的边界。页面级回退见 [回退机制-设计.md](回退机制-设计.md)；拆件与组装见 [拆件建模-设计.md](拆件建模-设计.md)。

## 第一部分：工作台撤销（Ctrl+Z）

### 1. 判断

- **有道理，而且和回退是两套机制。** 回退（返回键 / Esc）回的是**页面**；撤销（Ctrl+Z）回的是**一步编辑**。Unity 没有"页面"，所以只有 Ctrl+Z；我们两者都要，互不碰：Esc 从不撤销编辑，Ctrl+Z 从不切页面。
- **边界沿用回退机制的同一条原则**：凡经 IPC 提交的事（组装成新版本、保存映射、生成、导入、发送到 Unity、回收站、密钥）**不撤销**；撤销只管"还没提交的本地草稿"。这正是用户说的"模型创建好了点击了保存就不该有回退"。
- 回退机制-设计 §6 已把"操作级撤销"明确留给以后——现在到了。

### 2. 现状（2026-10-26）

- **图片编辑器已经有撤销 / 重做**：`features/imageprep/session.ts` 维护 `undoLog` / `redoLog`（蒙版编辑由 worker 撤销，色阶编辑靠恢复前值；超出 `TOOLS.undoDepth` 的旧步永久化）；`ImagePrepDialog.tsx:583` 绑 `ctrl+z`，`:584` 绑 `ctrl+y` / `ctrl+shift+z`，`whileModal: true, inInputs: false`。**键位与习惯以它为准**，新历史不另起一套。
- **手动组装面板**（`workspace/panels/PartsManual.tsx`）：`rows` 是本地 `useState`，`update()` 直接写视口（`viewer.setPartTransform`），`reset()` 回到 `initial`；**没有历史**，换资产 / 离开页面即丢，也没接离开守卫（0.1.13 的已知限制）。
- **动作设计台**（`motion/MotionPanel.tsx:96–134`）：`draft`（关节更正 + 朝向 + 配方），`mappingDirty` 已接离开守卫；只有「保存映射」一个提交点；**没有历史**。
- **热键**（`hooks/useHotkey.ts`）：带 Ctrl 的组合键默认在输入框里也触发（`inInputs ?? (ctrl||alt||meta)`），要让输入框保留浏览器原生撤销必须显式 `inInputs: false`；事件已 `defaultPrevented` 的不再处理——所以图片编辑器开着时它先接住，外层不会重复撤销。
- 依赖里只有 `zustand 5` 与 `react-router 7`，没有 immer / zundo；草稿都很小（十几个部件变换、一张映射表），**快照式历史足够，不引新依赖**。

### 3. 参照：Unity / Blender / Godot，我们取什么

| 来源 | 做法 | 取舍 |
|---|---|---|
| Unity | Edit → Undo / Redo（Windows：Ctrl+Z / Ctrl+Y）；[Undo History 窗口](https://docs.unity3d.com/6000.0/Documentation/Manual/UndoWindow.html)列出每一步、点一条回到那一步（6.1 起在 Window → General）；拖动等连续操作合并为一步（`Undo.CollapseUndoOperations`）；**选择变化也进栈**（社区自 2010 年起抱怨它弄乱历史）；资产删除不进栈（进系统回收站）；保存后仍可撤销 | 取键位、每步有名字、连续操作合并、保存不清栈、"提交不进栈"；**不取**"选择进栈" |
| Blender | Ctrl+Z / Ctrl+Shift+Z；Edit → [Undo History](https://docs.blender.org/manual/en/latest/interface/undo_redo.html)；偏好里有 [Undo Steps 与内存上限](https://docs.blender.org/manual/en/latest/editors/preferences/system.html)；载入文件清栈、保存不清栈 | 取"步数上限"、"换文档清栈、保存不清栈" |
| Godot | `UndoRedo`：每个动作有名字，do / undo 成对，合并模式（连续拖动 MERGE_ENDS） | 取"按 key 合并连续编辑" |
| Figma / Godot 编辑器 | 选择、视口缩放平移不进撤销栈 | 取：**选择、相机、面板开合不进栈**；撤销后高亮被改的那个部件，让人看见动了什么 |

### 4. 定义：撤销的是什么、不是什么

- **撤销对象 = 工作台里还没提交的本地草稿**：手动组装的部件位置 / 缩放 / 朝向与「重置」；动作设计台的关节更正、朝向、配方参数；今后组装工作台的层级、重命名、显隐。
- **不撤销**：一切经 IPC 提交的事。提交之后草稿历史**保留**（Unity 保存后仍可撤销），只是把 `savedIndex` 记到当前位置——于是 **脏 = index ≠ savedIndex**，这个脏标记直接喂给 0.1.13 的离开守卫（`useLeaveDirty`），不再各处手写 `dirty`。
- **不进栈**：相机、选择、面板开合、模块切换。
- **栈按"文档"隔离**：一份历史对应 (资产, 版本, 面板)。换资产 / 版本不丢（存在 store 里），切回来还在；关应用即清（Unity / Blender 都不跨重启保留）。
- **上限 100 步**，每步快照 < 10 KB；超出丢最旧的（Blender 的 Undo Steps）。

### 5. 机制

- **`createHistory<T>()`**（`src/renderer/src/lib/history.ts`，纯函数 + 一个 zustand store 持有所有文档）：
  `{ past: Step<T>[], present: T, future: Step<T>[], savedIndex }`，`Step = { label, before, after, key?, at }`。
  `commit(next, label, key?)`：同一 `key` 且距上一步 < 500 ms → 合并进上一步（拖拽、连续敲数字只算一步，Unity 的 Collapse / Godot 的 MERGE_ENDS）；否则压栈并清空 `future`。
  `undo()` / `redo()` 返回新的 `present` 与这一步的 `label`、被改的部件名；`markSaved()`；`canUndo` / `canRedo`；`clear()`。
- **面板怎么接**：面板不再各自 `useState` 草稿，而是 `const h = useHistory(docKey, initial)`；编辑 = `h.commit(nextRows, '移动 尾巴', 'tail.position')`，再把 `present` 写回视口与表单（手动面板的输入框是非受控的，沿用 `generation` 重 key）。数字框**失焦或回车**算一步提交；gizmo 拖拽以 pointerup 收尾。
- **键位**：`useHotkey('ctrl+z', h.undo, { enabled: h.canUndo, inInputs: false })`，`useHotkey(['ctrl+y', 'ctrl+shift+z'], h.redo, …)`。焦点在输入框里的 Ctrl+Z 归输入框（浏览器原生撤销文字）；焦点在视口 / 面板空白处归历史；模态层开着不触发（默认）；图片编辑器对话框先接住自己的。
- **谁接 Ctrl+Z**：同一时刻只有一个"活动面板"（屏上那个），注册到 `useActiveHistory`；顶层不设全局处理器，避免两套历史抢键。
- **工具条**：面板顶部 ↶ ↷ 两个按钮（禁用态；提示"撤销：移动 尾巴 Ctrl+Z"）+ 「历史」下拉：最近 N 步，点一条跳到那一步（Unity Undo History 的简化版，先不做独立窗口）。
- **与 Esc 的关系**：Esc 不碰历史；离开时守卫按 `index ≠ savedIndex` 问；「留下」保留历史，「离开」丢草稿（历史随之清掉）。
- **提交点的表现**：手动面板的「按当前位置重新组装」成功后 `markSaved()`，工具条显示"已组装为 v{n}"；继续改仍可撤销到组装前的位置，但 v{n} 不会消失——这就是"提交即提交"。

### 6. 第一批接入与顺序

1. 手动组装面板（用户当下最痛：试了几次拼接，想退一步没得退）。
2. 动作设计台（映射更正 + 配方），顺手把 `mappingDirty` 换成 `savedIndex`。
3. 组装工作台（0.1.13 之后的方向：Unity 式层级 / 检视器 / gizmo）**从第一天就建在这份历史上**，而不是先做再补。

### 7. 测试

- 单元：`history.ts` 纯函数——压栈、合并（同 key 500 ms 内）、undo / redo、上限、`savedIndex` 与脏判断、clear。
- 端到端（真实应用）：手动面板改两个数 → Ctrl+Z 两次 → `viewer.listPartNodes()` 回到原值 → Ctrl+Y 回来；焦点在数字框里按 Ctrl+Z 历史不动；改完不组装就离开 → 守卫弹；组装后再改 → 守卫仍按新 `savedIndex` 判。
- 回归：图片编辑器开着时 Ctrl+Z 仍归它（`sweep` / `imageprep` 现有 spec）。

## 第二部分：资产文件夹

### 1. 判断

- **有道理。** 库现在只有"类别"一个维度（首页 全部 / 角色 / 道具 三个芯片，`home/gallery/Gallery.tsx:150`），拆件一旦开始，一个角色就生出十几个部件和组装体，平铺必然乱。
- **做"虚拟文件夹"，不动磁盘文件。** 库里的文件按 id 存放（`assets/<id>/…`），搬迁 / 备份 / 日志都围绕它（`main/core/library/relocate.ts`、`journal.ts`）；文件夹只是数据库里的归属关系，建、删、改名都不触碰文件，也不影响已送进 Unity 工程的东西。
- **大部分文件夹可以自动建出来。** 部件与组装体早就带着来源标签：`part`、`part-role:<角色位>`、`part-of:<资产>`（`workspace/parts/mould.ts:13`、`parts/assemble.ts:63`）。真实库（2026-10-26，只读查询）：29 个资产，其中 **17 个** 带 `part-of:人形角色`（8 个部件 + 9 个组装体），12 个没有归属（大肥鱼、星璇、几个头、model）。一次迁移就能把 17 个归进「人形角色」夹，用户再把它改名成「大肥鱼」、换封面即可。

### 2. 现状

- `assets` 表已有 `tags`（JSON，自由文本，上限 `TAGS_MAX`，进全文索引）、`favourite`、`category`、`batch_id`、`deleted_at`（回收站 + 恢复已成熟：`library:delete` / `library:restore`）。`AssetQuery` 能按类别 / 标记 / 等级 / 来源 / 收藏 / 批次 / 日期筛，**不能按标签筛**（标签只在搜索里命中）。
- 图片表 `images`：concept 49、source 7、prepared 172——**封面有现成素材**（概念图 / 原图）。
- 资产页（`features/assets/`）：工具条 + 筛选面板 + 网格 / 列表 + 选择条 + 标签对话框；右键菜单六项：在工作台打开、发送到 Unity、导出、移到回收站、恢复、永久删除。
- 工作台右栏「资产」页签（`workspace/rail/AssetsTab.tsx`）：一条按时间倒序的搜索列表，无分组。
- Unity 送出目录：`Assets/Modelwright/{Slug}_{id6}`，`NamingConvention.folderPattern` 支持占位符 `{Slug}` `{id6}` `{Category}`（`main/core/unity/service.ts:718`）。

### 3. 参照

| 来源 | 做法 | 取舍 |
|---|---|---|
| Unity Project 窗口 | 真实文件夹（**唯一归属**）+ Labels（多对多标签）+ Favorites（保存的搜索） | 取"唯一归属的文件夹 + 标签负责交叉"；我们的标签、收藏已经在 |
| Blender Collections | 多对多、可嵌套 | 不取多归属（总览里一个资产只该出现一次；"移动到"语义才清楚） |
| Lightroom | Folders（物理）+ Collections（虚拟）+ Smart Collections（按规则） | 取"虚拟"；"规则夹"（如 骨骼+动画）留到以后 |
| 资源管理器 / Finder | 新建、F2 重命名、拖拽移动、删除确认 | 取键位与拖拽 |

### 4. 规则（把用户的愿望补全）

1. **唯一归属，一级深度**：每个资产属于且只属于一个文件夹；这一版不嵌套。交叉需求用标签与收藏。
2. **两个系统文件夹，永远在**：「通用」固定第一位（用户说的"通用资产"：示例模型、常用道具、跨角色复用的东西），不能删、可改名；「未归类」固定最后一位，是收件箱——没有归属的资产都在这里，保证总览里**什么都不会消失**。
3. **自动归档**：建立拆件计划时，为基础角色建夹（名 = 角色名，封面 = 它的概念图 / 原图），之后生成的部件、组装体、头部变体自动归入（写入时按 `part-of` 归档）；已有库由迁移一次性归档。批量生成（`batch_id`）的产物归入"当时打开的文件夹"。
4. **新资产的默认去处 = 当前打开的文件夹**（像 Unity 在选中的 Project 文件夹里新建资产）；在「全部」视图里新建的进「未归类」。
5. **封面**：默认取夹内第一个资产的概念图 → 原图 → 缩略图；「⋯ → 更换封面」可从夹内任一资产的图片或本地图片选。满足"图标就用上传的那张图"。
6. **文件夹卡的「⋯」**（右上角）：打开、重命名（F2）、更换封面、上移 / 下移、删除文件夹。**删除文件夹不删任何资产**：里面的资产回到「未归类」，弹确认说明这一点。
7. **资产卡 / 多选的「⋯」与右键**：新增「移动到文件夹…」（列出文件夹 + 新建…）、「设为文件夹封面」；原有六项不变。支持把资产**拖到**文件夹卡上。
8. **总览结构**：资产页顶部一行文件夹卡（封面 + 名字 + 数量），下面是当前夹的内容；进入某夹后面包屑「全部 › 大肥鱼」；「全部」视图保留（跨夹平铺 + 搜索 + 现有筛选）。首页「我的资产」同样先显示文件夹行，再是最近资产；类别芯片继续作为夹内筛选。
9. **工作台右栏资产页签**：按文件夹分组（可折叠），当前资产所在夹默认展开，搜索仍跨夹。
10. **回收站**：移到回收站的资产保留 `folder_id`，恢复时回到原夹（夹已删则回「未归类」）；夹的数量不计回收站里的。
11. **Unity**：`folderPattern` 新增占位符 `{Folder}`（文件夹的 ASCII slug，系统夹为空时退回默认）；默认模式不变，想要 `Assets/Modelwright/DaFeiYu/Hair_3f9a2c` 的用户自己把模式改成 `{Folder}/{Slug}_{id6}`。
12. **Esc 优先级新增一层**（回退机制-设计 §3）：资产页处在某个文件夹里 → 回到文件夹总览；排在"关抽屉 / 清选择"之后、"回退一页"之前。进入文件夹是页内状态（URL 参数 `replace`），**不进历史栈**。

### 5. 数据与接口

- **迁移 7**（`main/core/library/schema.ts`）：
  `folders (id TEXT PK, name TEXT, slug TEXT, cover_image_id TEXT NULL, cover_path TEXT NULL, sort INTEGER, system TEXT NULL /* 'general' | 'inbox' */, created_at, updated_at)`；
  `ALTER TABLE assets ADD COLUMN folder_id TEXT NULL` + 索引；
  迁移同时：建两个系统夹；按 `part-of:<id>` 为每个被引用的资产建夹并归档其部件与组装体，被引用的资产本身也进该夹；其余 `folder_id = NULL`（= 未归类）。
- **契约**（`shared/ipc/contract.ts`）：`library:folders`（列表 + 数量）、`library:createFolder`、`library:updateFolder`（名字 / 封面 / 顺序）、`library:deleteFolder`（资产回收件箱）、`library:moveToFolder({ assetIds, folderId })`；`AssetQuery.folderId?: FolderId | 'inbox' | null`；`LibraryFacets.byFolder`；`AssetPatch.folderId`；`library:changed` 新增 reason `'folders'`。
- **名字**：中文随意；`slug` 走现有 `toSlug`（ASCII PascalCase），供 `{Folder}` 用；同名加数字后缀（沿用资产 slug 的规则）。
- **搜索**：`assets_fts` 不变；夹名不进全文索引（夹本来就在屏上）。

### 6. 不做（这一版）

- 不做多级嵌套、不做多归属、不做规则夹（智能文件夹）。
- 不把标签页改成"按标签筛"（另一件事；但若要做，`AssetQuery.tags` 一列即可）。
- 删除文件夹不删资产；不做"删除夹并连同资产进回收站"的组合动作。

### 7. 测试

- 单元：迁移把 17 个 `part-of` 资产归入其角色夹，系统夹建立且不可删；删除夹后资产回「未归类」；`facets.byFolder` 不计回收站。
- 端到端（真实应用）：新建 → 重命名 → 把资产移进去（菜单与拖拽各一次）→ 换封面 → 删除夹后资产回收件箱；夹内 Esc 先回总览再回退页面；工作台右栏分组展开当前夹。
- 真机：当前库迁移后的总览截图核对（预期三个夹：通用、人形角色（用户改名为大肥鱼）、未归类）；Unity 用 `{Folder}/{Slug}_{id6}` 送一次，确认子目录。

## 实现记录（2026-10-26，随 0.1.14 一起做了，两件一起发）

用户同意了上面的分析，并加了一条硬要求：**不能因此产生幽灵文件夹、不能写到未知的盘（包括直接写 C 盘），一定要能随 app 一起完整删除，存放位置要能自由查看**——这是最要把关的。于是先做了一次只读审计（应用写盘的七处位置，见验收指南 0.1.14 §2），发现部件组装的 GLB 一直写在系统 `%TEMP%` 且从不清理（本机约 892 MB），顺手一起修了。

**定下来的四个问题**：唯一归属；一级；选择不进撤销栈；系统夹叫「通用」「未归类」。

**文件夹，照第二部分做了**，差异如下：
- 文件夹是数据库里的行（`folders` 表 + `assets.folder_id`），没有任何磁盘目录；封面要么引用现有输入图片，要么把本地图片当输入图片存进 `inputs/`——不新增任何写盘位置。
- 「未归类」没有自己的行（`folder_id IS NULL`），所以不能改名；「通用」是行（`system = 'general'`），可改名不可删。
- 自动归档在提交时做（`folderForNewAsset`），不是建拆件计划时：效果一样，且导入、生成、批量都覆盖；迁移 7 对旧库做一次。
- 工作台右栏没有做分组折叠，做的是一个文件夹下拉（列表是分页的，分组跨页不好做）。
- 「移动到」在三处：卡片 ⋯（新增）、右键菜单、选择条；加上拖拽到文件夹卡。

**Ctrl+Z，照第一部分做了**，范围收窄了一处：动作设计台只有关节更正和朝向进历史，模板 / 滑杆 / 名称没有（它们不是会丢的草稿——保存配方时才成为文件的一部分）。手动组装面板全量接入。

**存储把关，新增**：设置 → 资产库 → 存储位置（七处路径、大小、打开）、清理缓存、删除本机全部数据（输入 ERASE，关库后删除，退出）；卸载程序自动清更新器缓存 / 桥接目录 / 旧临时目录，并两次询问是否删应用数据、资产库；组装 GLB 改写到应用自己的 temp，启动时删旧的系统临时目录；桥接目录空了就删。

## 组装台（2026-10-26 晚，用户试过 0.1.14 的手动面板之后）

用户的反馈原话：「一进来发现摆件选择不了，点击模型也无法选择……模仿 Unity 的建模页面，可以选择单独的摆件并且有各种方便移动拼装的」；接着：「在左侧单独延申出来一个这样的工作台，为他赋予单独的标签，这样就不占用我们这个主场景了」；再接着：「考虑好各个位置的快捷跳转」「思考好各种遍历功能和联动，同时组装台本身也要功能丰富齐全以及便利而且不复杂」。

**做法（0.1.15）**：
- 视口侧新建 `viewer/partEditor.ts`：悬停框、点选、TransformControls 手柄（W/E/R/Q），把摆放约束在"位置 + 等比缩放 + 偏航"内，Ctrl 吸附，F 对焦；Viewer 暴露 `setPartEditing / selectPart / setPartGizmoMode / focusSelectedPart / setPartVisible` 与 `partSelect / partEdit` 事件。
- 新模块「组装台」（`assemble`，左栏拆件之后）：工具条 + 撤销条、层级（点选 / 双击对焦 / 眼睛隐藏 / 单件恢复）、检视器（只显示选中件的数字）、方向键微调、下一步（后处理 / 发送 Unity / 试机场 / 回拆件）；不是组装体时列出库里的组装体。旧的 PartsManual 面板删除，拆件模块对组装体只留一个入口。
- 跳转：资产页 / 首页打开组装体直接落到组装台；拆件模块组装完成后「去组装台调整摆放」；组装台草稿在历史里，切模块、换资产不丢——离开守卫改成"只在离开工作台页面时问"（`LeaveGuardText.keeps`，动作设计台同样）。
- 验收：`tests/e2e/assemble.spec.ts`（用两件立方体组装体）+ 真机。

**取舍**：手柄的旋转只给 Y 环、缩放按等比处理（摆放模型就是这三样）；没有多选、没有复制 / 删除件（件来自拆件方案）；隐藏是视图状态不进历史；位置图（§7c）仍未做。

**真机复核（2026-10-26 晚）发现的三件事**：
- 手柄画得出来但抓不住：`partEditor.ts` 把 `getHelper()` 的整棵树放到 HELPER_LAYER，而 TransformControls 用模块私有的 Raycaster（只看第 0 层）去碰 `_gizmo.picker` 和 `_plane`，于是永远碰不到，拖动落到了轨道相机上。改成只把画出来的手柄放辅助层、拾取体和平面留在第 0 层（两者本来不可见，抓图不受影响）。端到端的 `assemble.spec` 现在真的拖一次 X 手柄（`viewer.partHandlePoint('X')` 给出手柄在画布上的位置），并核对相机没动（`viewer.viewpoint()`）。
- 按住手柄不动再松开会记一步「移动」并可能改选择：松手时 TransformControls 已清掉 `axis`，所以在按下时记住"这次按在手柄上"（`pressOnGizmo`），拖动期间没有 `objectChange` 就不发 final（`dragChanged`）。
- 组装体来源的角色被删后，面板在黄条之外还弹「找不到对象」：`library:get` 的 not_found 现在吞掉（`isErrorKind`），只留黄条。
- 另：端到端窗口尺寸在显示缩放为 125% / 187.5% 时会被边框凑成 1442 × 903，严格尺寸检查失败；`launchApp` 现在给 Electron 加 `--force-device-scale-factor=1`。

**用户试用后的第一条反馈（2026-10-26 晚）**：「放大缩小和旋转时候有很明显的卡顿感，特别是由静止转为第一下拖拽的时候」。先量再改：用 Playwright 驱动构建版在真实库副本上打开「人形角色·组装」（292 万三角），CDP 采样 + 逐帧计时（脚本留在 实验用例（未公开））。拖拽本身 17 ms/帧，问题在悬停：`partEditor.holderAt` 对全部件做 CPU 射线，three 默认逐三角、无 BVH，每次指针移动 143 ms、悬停 6 帧/秒；按下手柄前最后一次移动排的那次射线把 pointerdown / 第一次 pointermove 压在后面，就是"起拖那一下"。改成 `viewer/partPicker.ts` 的 GPU 取色（编号颜色 → 1 × 1 渲染目标 → `readRenderTargetPixelsAsync`），每次 < 1 ms；首次编译 ~100 ms 由 `warmUp` 在打开组装台时承担。没有引入 three-mesh-bvh：BVH 要为 300 万三角建树（秒级、几十 MB），GPU 取色零预处理、零额外内存、逐像素精确。

**第二轮反馈（2026-10-26 晚，用户：「操作手感还是比较糟糕」）**：缩放要加减按钮、Q / E 左右转 90°、框选后按轴对齐、"身子吸到脑袋上非常费劲"、再去看各家公开文档学技术。调研与取舍写在 docs/组装台-交互调研.md。做法：纯函数 `parts/placement.ts`（对齐 = Blender Align Objects 的 Active + 三种 side；贴合 = Unreal End 推广到六向，面贴面、只算脚印重叠的件；绕基准件旋转 / 缩放 = Unity Pivot 模式）与 `viewer/snapping.ts`（一维磁吸，Figma 智能参考线搬到被拖的轴上，阈值屏幕 8 px 折算到件的深度）；`partEditor.ts` 改成多选（有序，最后一个是基准件，手柄在它上，其它件随动），Shift 拖框选用 `partPicker.pickRect` 渲染框内区域读回（看得见才算），Alt 暂关磁吸，Ctrl 仍网格吸附；面板加快捷操作行、对齐组、贴合菜单，工具键改 1–4。
