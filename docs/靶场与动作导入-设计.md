# 靶场与动作导入 — 设计（0.1.15）

> 本文是私有源码库里同名设计文档的公开版：内容相同，去掉了本机路径和内部审计 / 实验文件的位置。源码中的文件名（如 `src/shared/motion/retarget.ts`）指私有仓库里的位置。

起因：2026-10-27 用户给了两条视频——A菌《震惊瘫坐！真的可以一张图直接生成游戏用角色了？！》（Charakuru：一张图 → 分部件图 → Tripo 2.0 → 调比例 → 全自动绑定（头发、尾巴带动力学）→ 导出 VRM → 套 Mixamo 动画 → 放进 Three.js 的射击 demo「大肥鱼拯救克劳德」）和派派wj《gpt6+tripo制作完整角色》（GPT 画三视图：头、头发、穿好衣服的身体分开 → Tripo 智能网格四边面 → GPT 操控 Blender 自动拼装、修网格、切表情、绑骨 → 导出 VRM）。用户的结论：拆件 + 拼装只能由用户自己上手，平台已经够用；要两条线并行（部件生成、整图一键生成），并把 Mixamo 动画和一个像样的射击验证场接进 app。

## 1. 动作导入（Mixamo 等）

**为什么不是接口**：Mixamo 没有公开 API，社区方案都是用 Playwright 驱动网页、带着 Adobe 登录态，随时会断，不适合放进发行版。所以走"本地下载 + 导入"：用户在 mixamo.com 下载（Format「FBX for Unity」、Skin「Without Skin」），在动作设计台一键导入。

**导入后发生什么**（`src/renderer/src/features/motion/MotionPanel.tsx` → `viewer/retargetSource.ts` → `shared/motion/retarget.ts` → `shared/motion/recipe.ts`）：

1. `library:attachAnimations` 把文件复制到版本文件夹（role `animation`；0.1.15 起接受 FBX / GLB / glTF；Unity 交付仍只带 FBX，`unity/assets.ts`）。
2. 用视口的渲染器把文件加载成 three.js 场景，`captureRestSkeleton` 取它自己的骨架，`AnimationMixer` 按 30 fps 逐帧采样：每根骨头在模型根坐标系里的世界旋转 + 髋的世界位置。
3. 两副骨架各自 `mapSkeleton` 成关节角色图（髋 / 脊柱 / 胸 / 颈 / 头 / 肩 / 上臂 / 前臂 / 手 / 大腿 / 小腿 / 脚 / 脚趾），`pairJoints` 按角色 + 左右配对；链长不同（Mixamo 三节脊柱对我们一节）按位置分段、取每段最深的源关节，弯得一样多。
4. 每帧每对关节：源关节相对自己静止姿态的世界旋转差 Δ → 用 F（两副骨架朝向差的偏航）转到目标坐标系 → 先用 A（目标骨骼静止方向到源骨骼静止方向的最短弧）把目标骨骼"摆成源的静止姿态"→ 再按模板同样的链式合成规则（子关节的差叠在父关节之上）换算成局部旋转。效果：**目标骨骼指向源骨骼此刻指向的方向**，T-pose 的源配 A-pose 的目标也对。髋位移按身高比缩放。
5. 结果是 `ImportedClip`（按关节**名字**绑定、固定帧率的局部旋转轨道），写进 `motions.json` 的 `imported`，和设计配方一样：视口动画条、试机场、靶场直接播；mesh worker 的 `motion` 步骤烘焙成真正的 glTF 动画，送 Unity 不需要 Humanoid。

**没做 / 已知限制**：手指、尾巴、耳朵、翅膀不搬（Mixamo 没有对应）；绕骨轴的扭转只跟源走，没有 Unity 肌肉空间那种约束，手腕偶尔会拧；没有脚接地 / IK（设计台本来也没有）；源文件最长两分钟（3600 帧）。

## 2. 靶场

`src/renderer/src/features/range/`：`logic.ts`（纯逻辑：武器表、弹药与射速状态机、散布锥、靶场布局、环数、射线 vs 圆盘 / 箱体、近战扇形；单测 `tests/renderer/range/logic.test.ts`）、`game.ts`（three.js 场景 `RangeGame`，复用试机场的 `player.ts` 装载与 `engine.ts` 的碰撞 / 步速）、`RangeStage.tsx`（HUD）、`RangePanel.tsx`（上场模型、武器架、操作、状态）、`store.ts`；模块 id `range`，图标 Crosshair，文案 `messages/range.ts`。

- **场**：室内靶场，八条靶道三档距离（10 / 18 / 26 m）的环靶、四个起落人形靶、远墙两块左右滑动的移动靶、三个会爆的油桶、三个给刀用的假人；射击线柜台、靶道隔板、掩体箱、侧墙与后挡墙（都是实体碰撞）。
- **武器**：手枪、冲锋枪、突击步枪、霰弹枪（8 粒）、狙击步枪（瞄准放大）、匕首、武士刀——全部由基本体拼成（`buildWeapon`），挂在模型**手骨**上：按关节角色找右手（没有就左手），枪管对准手骨方向；没有手的模型（道具、神经元骨架）端在胸前。
- **动作**：按片段名认角色（`classifyRangeClips`）：持枪待机 aim（Rifle Idle）、开火 fire（Firing Rifle）、装填 reload、近战 melee（Stab / Slash）、受击 hit，加上 idle / walk / run / jump；缺的回退（aim→idle，fire / melee→任意动作片段，没有动作片段就身体一抖）。
- **操作**：点画面锁定鼠标（Pointer Lock；拒绝时拖动转镜头，e2e 靠这个），左键 / J 开火（自动武器按住连发），右键瞄准，R 装填，1–7 / 滚轮换武器，K 挥击，Space 跳，Shift 跑，T 重开。
- **验证点**：枪是否长在手上（手骨 + 方向）、走位时的 walk / run 与瞄准时的 aim 是否顺、开火装填是否有对应片段、模型尺寸异常时的 fitScale、神经元模型没有手时的胸前持枪。

## 5. 第二轮（0.1.16，2026-10-27）：用户说「整体很劣质、移动也不对」之后

先录像再动手（实验用例（未公开），真角色 + Soldier 片段，逐帧截图 + `probe()`）。查出来的硬伤，按严重程度：

1. **HUD 根本没显示过**。`RangeStage` 在 React 渲染完子节点后把 canvas `appendChild` 到最后，canvas 是 `position:absolute; inset:0`，同层后画的盖住先画的——得分、弹药、模型信息、准星全在画布底下，只有后来才插进来的节点（操作提示、点击提示）露出来。试机场同样。改成 `element.prepend(canvas)`。
2. **A / D 左右镜像**。`camRight = (fz, 0, −fx)` 其实是镜头的左；右边应是 forward × up = (−fz, 0, fx)。靶场和试机场的引擎都改了。
3. **枪口朝后朝下**。枪管沿前臂，前臂在普通行走片段里垂着——探针量到枪口在脚底后方。现在瞄准 / 开火时武器插槽每帧转到准星方向（`orientWeapon`，按 `aimPose` 渐变），没有持枪待机片段的模型由 `aimArms` 把右臂（和长枪的左手）按世界方向抬向准星——只用骨骼的世界位置算，Tripo / Mixamo / 神经元的手臂角色都能用。
4. **镜头贴脸、角色占半屏**。自由移动 `max(3.4, 2.6h, 5.5r)` 跟在身后；持枪 `max(3.0, 2.3h, 5r)` 过肩（偏右 0.55h、枢轴 0.72h）；右键放大时按 `1/√zoom` 退远，角色保持大小，远处放大；镜头到角色之间有立柱 / 平台就拉到它前面（`rayBox` 外扩 0.25 m）。
5. **控制方式**。自由移动时角色朝走的方向转身（walk / run）；右键或开火 / 挥击后 1.4 s 内面朝准星（`aimMode`），用 strafeLeft / strafeRight / back 片段，没有就退回 walk。角色朝向的"右"也是 (−fz, 0, fx)——第一次写反了，录像里按 A 播的是 Strafe Left 但人往右走。
6. **场地和对手**。圆形霓虹竞技场（半径 24 m：发光网格地面、三圈光环、24 根灯柱、四根带灯条的立柱、三块平台、七块环靶三档距离、四块起落靶、两块移动靶、四个能量核心），UnrealBloomPass 泛光；四个哨兵（`BOT`：60 血、1.6 m/s、贴身 1.4 m 每 1.3 s 砍 8）从边缘出生点逼近，按角色身高缩放（1 m 的 Q 版打 0.6 m 的哨兵），挡在镜头和角色之间变成 18 % 透明；玩家 100 血，归零播 death 片段（没有就倒下）3 秒后起点复活，`deaths` 计数，分数保留；T 重开。
7. **片段角色**扩到 13 个：idle / walk / run / back / strafeLeft / strafeRight / jump / aim / fire / reload / melee / hit / death；aim 先认 "aim"，再认 rifle / pistol / gun（"Rifle Aiming Idle" 优先于 "Rifle Idle"，后者就当 idle）。
8. 文案里的 Mixamo 地址改成 `https://www.mixamo.com/#/`，并提示走跑侧移勾 In Place。

真机素材：用户登录的 Chrome 里经 Claude in Chrome 下载了 14 条（FBX for Unity / Without Skin，走跑侧移 In Place）到本机的下载目录：Rifle Idle、Rifle Aiming Idle、Rifle Walk、Backwards Rifle Walk、Rifle Run、Firing Rifle、Reloading、Strafe Left、Strafe Right、Rifle Jump、Stabbing、Great Sword Slash、Hit Reaction、Dying。导入到 Tripo 绑骨的人形角色：14 段、23 关节全对上；靶场认出全部 13 个角色（近战 = Great Sword Slash，按字母序先到）。

真机（本机 app 换成 0.1.16 后，经文件对话框把 14 条 FBX 分两批导入——文件名框有长度上限，一次最多七八个带引号的名字）发现两处补修：(a) 同一角色里有 Soldier Walk 和 Rifle Walk 时选了前者——现在每个角色先找带 rifle / pistol / gun / shoot / aim 的片段；(b) 指针锁定刚接管时的光标跳变（一次几百像素）被当成转视角，镜头瞬间俯到头顶，角色看起来像趴着——单帧位移超过 300 px 的事件丢弃。

没做 / 待看：哨兵只有一种、没有远程哨兵；没有音效；没有掩体蹲伏；镜头碰撞只对箱体不对哨兵（哨兵改透明）；Great Sword Slash 和 Stabbing 二选一（没有按武器分近战片段）。

## 6. 第三轮（0.1.17，2026-10-27 晚）：按整改任务书

一份独立审计用真实资产离线演算指出的问题，逐项在真角色 A 上复现、修、再量：

1. **朝向**：A 的骨架前向是 +X（脚趾、手臂展开方向都如此），游戏的身体正前是 +Z——角色横着走。`preparePlayer` 现在用动作设计台同一份映射（含用户的前向修正）得到轴，`forwardYaw` 把根转到 +Z，然后再居中落地；rest 骨架留在模型自己的坐标系里供动作用。
2. **根位移**：`removeRootTravel` 把髋部位置轨道的净水平位移（在髋父空间→模型空间判断）按线性趋势去掉，保留摆动与起伏；靶场 / 试机场对走 / 跑 / 后退 / 侧移角色应用。
3. **动作生命周期**：`playground/clipPlayer.ts`——一次性片段打断必 stop、再按重启、`stopAll(then)` 清掉全部并同帧求值；淡出结束的 action 回收。
4. **开始 / 暂停与游戏时钟**：`gameMs` 只在开始且未暂停时累加；所有冷却、计时、HUD 标记用它。
5. **头部**：`retarget.ts` 对叶关节不做 rest 方向对齐。
6. **步态配速**：`locomotionSpeed` 估计片段的行进速度（有位移取位移，原地取双脚前后最大间距×2/周期），游戏按 控制器速度 / 片段速度 设 `timeScale`。
7. **部位摆动模板**（`templates.ts` `part`）：待机基础 + 单部位摆动；面板选部位 / 左右，已存配方可载入。
8. **GLB 出口**：`viewer/glbExport.ts` + `app:saveBytes` + 面板按钮；契约：文件里是视口能播的片段（同名留一个），不含靶场运行时的朝向校正和原地化。
9. 保存 / 继承 / 标记 / 文案：见 RESULTS.md 08 / 06 / 07 / 09 / 10。

手拼路线（B）的真实缺口：本地神经元绑定只找到尾巴；没有服务商绑骨就没有可用的人形绑定。

## 7. 第四轮（0.1.18，2026-10-28 凌晨）：闭环命令

1. **输入**：`mainWindow.ts` 的 `APP_PAGE_PERMISSIONS = ['clipboard-sanitized-write', 'pointerLock']`（只对应用自身页面）；`RangeGame.requestLock` 记住拒绝（Promise / `pointerlockerror` / 1 s 无应答）后左键直接开火；Shift 非重复 keydown 切换 `runMode`；默认 `camPitch` 0.04。
2. **尺度**：`viewer/bounds.ts` `visibleBounds`（蒙皮按 skin 算）供 `preparePlayer` 拟合；`poseToBind` 比较恢复前后的可见高度，比值超出 [0.5, 2] 就撤销（Xbot 这类"顶点 1/100 + 绑定 ×100"的文件）。
3. **组合**：`upperBodyClip`（spine → hands 的轨道）+ `ClipPlayer.addClip / playOverlay / overlaying`；靶场 fire / reload 走覆盖层，不再 `actionUntil`。
4. **步幅**：`locomotionSpeed(clip, player, travel, axis)`：前进 +Z / 侧移 +X（校准后的身体轴），双脚前后差符号变化 / 2 = 周期数；`removeRootTravel` 的父→根换算用完整矩阵（含缩放）。
5. `tickWeapon` 按 `cooledAt` 增量衰减；`partJoints` 不跨侧回退；`saveRecipe` / `removeRecipe` 以写入结果决定提示；`readMotions` 对 schema 无效抛错；导出资格计入 `version.stats.animations`。
6. **Unity**：Unity 6 批处理探针（`-probeReimport`，Generic）验证导出 GLB：A（HumanA_test）与赏金猎人（HunterP_test，两次导入一致）。

## 8. 第五轮（0.1.19，2026-10-28）：两场共用输入、训练设置、真实帧统计

- **输入**：`features/playground/lockInput.ts`（类 `LockInput`）两场共用。点画面 → `requestPointerLock`；只有 `document.pointerLockElement === canvas` 才算接管（`locked`），1.5 秒无应答或 `pointerlockerror` 记为被拒（`refused`，保持暂停并提示）；首次接管的点击不开火。已销毁后迟到的锁定在 5 秒内立即交还。Esc 在游戏里 `preventDefault + stopPropagation` 后释放（应用的返回不会收到）。失焦、`visibilitychange`、画布失焦、切模块 / 换模型（dispose）、最小化都会 `release` 并清按键。最小化来自主进程的窗口状态事件 `window:state`（`lib/windowState.ts`）：`backgroundThrottling:false` 时页面可见性不可靠。Shift：非重复 keydown 切换 `runMode`，暂停恢复保留，`resetRun()` 在重开时回到行走。实验室钩子 `labEngage()` 只在测试里代替真实授权。
- **帧统计**：`features/playground/frameStats.ts` 记原始 rAF 间隔（4096 环形），p50 / p95 / p99、> 50 / > 100 ms、恢复首帧单列；模拟仍用受控 dt。`renderer.info.autoReset = false`，每帧手动 reset，累计所有 pass。真暂停与最小化不再绘制（`draws` 计数可验证），尺寸或设置变化时按需重绘一帧。
- **动作**：`clipPlayer.ts` 的分层（`#lower` / `#base-upper`）让开火 / 装填覆盖层独占上身，覆盖层结束后基础上身 0.12 秒淡回；整身 `play(once)`（死亡）会先停掉覆盖层。`player.ts` 的步幅方向用父节点坐标系下校正过的身体前向。试机场的片段分类优先正向行走（`NOT_FORWARD` 排除 Backwards / Strafe 等）。
- **训练设置**：设置 `ui.range { bots: false, invincible: true }`（首次默认 AI 关、无敌开），面板 `TrainingFields` 改设置，`RangeStage` 用 `setTraining` 实时应用：关 AI = 撤下哨兵、不追击不攻击不重生、射线和 HUD 不再计入；无敌 = 共同伤害入口直接返回（不扣血、无受击动作 / 红闪 / 镜头冲击 / 死亡）。不重载角色、不重建渲染器、不清弹药分数；`locked` / `paused` 不持久化。
- **画面**：Bloom 0.32 / 0.35 / 0.9，地面去掉细网格（重复 12、各向异性 8），脚下圈改为 0x8a4a2a、不透明度 0.32 的细描边，瞄准切换用 `aimBlend` 平滑。

## 10. 姿态与体验闭环（0.1.19 草稿，2026-10-28 傍晚）

起因：用户看到标准人形 U 太空人持枪待机时整个上身侧歪。独立审计用真实资产离线复现并单变量反证：重定向把胸部的「参考方向」取成了最深子树——U 的胸骨选到左锁骨、源 Mixamo 胸骨选到右肩，两者做固定最短弧对齐（70.9°），源骨架完全静止时目标也侧倾约 20.6°。这个错误被如实地烘进了动作文件，也被如实地导出、在 Unity 里播放：跨端一致证明的是传递正确，不是动作正确。

### 10.1 躯干参考方向（retarget.ts）

- 只改重定向内部的对齐参考，不动 `RigJoint.direction`（自定义配方的摆动、骨架分类都在用它）。
- 髋 / 脊柱 / 胸 / 颈：参考方向沿**本躯干**取（`trunkPath`）——只穿过未分配的 other 和 helper，不进四肢、尾巴、耳朵、翅膀；按层级距离取最近的躯干后继，与子节点存储顺序、子树深度无关；同距两个躯干后继（两条颈）算分叉。
- 源与目标的参考端点要对应（`trunkReference`）：优先取配对关系给出的那一节，其次取同角色的第一节；目标没有颈时用「胸 → 头」对源的「胸 → 头」，不是对「胸 → 颈」；端点距离不足骨架 1% 的（Tripo 的 Hip 与 Waist 同位）顺延到下一节。
- 头是躯干末端：两边都没有后继时保持绑定朝向、只取源动作增量（沿用 0.1.17 的叶关节规则；面部骨、头顶 helper 不当成躯干延续）。
- 找不到可对应参考或分叉时，该关节回退为保持绑定朝向，并在 `RetargetReport.fallbacks` 里列出；不猜另一个肩，不强制对齐世界 Y，不全局关闭方向校正。四肢的 A/T 姿势适配照旧。
- 实测（真实网格、真实 Rifle Idle 整周期 258 帧，髋 → 首个颈骨的侧倾）：修前 −21.68° … −20.14°，修后 −0.94° … 0.59°，源动作 −0.98° … 0.53°，修后与源逐帧最大差 0.061°；走 / 跑 / 开火 / 装填与源的最大差 0.095° / 0.127° / 0.53° / 0.59°；源胸部子节点倒序后输出逐分量差 0；旧 U65 同样回正；A 的小幅偏差（约 1.7°）也随之消失。

### 10.2 按原附件更新已导入动作

- 修规则不会改已经烘进 `motions.json` 的旧轨道。动作设计台新增「按原附件更新已导入动作」：读取版本快照（含文件哈希）→ 逐个已保存的动作附件加载、按原片段帧率和帧数重新取样、用当前保存的映射重定向 → 先给出核对结果，确认后才保存。
- 只换轨道：动作 ID、名称、来源、帧率、帧数、创建时间、顺序、整份映射和设计配方都不变（`checkRefresh` 逐项核对，任何别的变化都不保存）。来源按「附件标签 · 原片段名」精确匹配；找不到、两个内容不同的文件对上同一来源、列表里名称或编号重复、重新取样帧数不一致：该条原样保留并列出。
- 旧规则判错的循环属性（`clipLoops` 用子串判断：Soldier 被当成 die，Firing、Dying 没被认出）单独列出、可选纠正；只纠正「值等于旧规则结果」的条目，不覆盖人为设置。
- 保存：`library:setMotions` 改为整份原子写入（`.part` 改名），同一版本的保存串行；更新带 `expectedSha256`，读取之后动作文件被改过就拒绝写入并提示重新读取；写入前在版本目录留 `motions.backup-original.json`（第一次的，永久保留）和 `motions.backup-previous.json`（上一次的）。
- 普通视口动画条新增「停止并恢复绑定姿势」，同时关掉动作设计台的实时预览（不会立刻被预览接回）；状态区分绑定姿势 / 预览 / 播放 / 暂停在某帧 / 一次性片段播完停在最后一帧；保存为一次性的片段在视口只播一次。
- 实测（实验副本）：带同名配方、一个歧义来源、一个缺失附件、一次中途另存：中途另存被拒、文件不变；更新 23 段、保留 2 段并列出原因、纠正 6 个循环属性；再次更新哈希完全相同；重启读到的是新轨道。正式主 U：25 段全部更新、6 个循环属性纠正，动作文件 `0adfcbfc85ac…` → `0278dfa1fb09…`。

### 10.3 扳机来源分开

- 靶场的键盘 J / Enter 和鼠标左键原来共用一个「按住」标志：松开 J 会清掉仍按住的左键，松开左键也会清掉仍按住的 J，J 按住时 Enter 松开同样。现在每个来源分别记（`TriggerSources`），有效扳机 = 任一来源按住；按下沿只在整体从松到按时算一次（一次拉动、单发武器只打一发）。暂停、失焦、死亡、未开始时清空全部来源。
- 回归：`tests/renderer/range/trigger.handlers.test.ts` 直接取 game.ts 里的三个处理函数在空对象上跑三种释放顺序和右键瞄准 + 左键组合；换回旧实现时这些用例失败。

### 10.4 帧统计的整段分位数

- 面板的 p95 / p99 原来取 4096 帧尾窗；现在整段另记直方图（100 ms 以下按 0.1 ms 分格并记每格最大值，更长的帧逐个保留），面板的 p95 / p99 / 最长 / 长帧次数 / 时长 / 平均帧率都是同一段（自上次「重新计时」起）的。

### 11.1 播放意图与会话归属分开

### 11.2 动作文件的一致性

- 令牌是同一次读取的原始字节的哈希（`readMotionsRaw`），内容和令牌来自同一份字节；数据库记录与文件不一致时以文件为准并修正记录。只核对已登记的文件，不把未登记的残留文件登记回来（不复活用户删掉的动作）；已登记却找不到是错误，不是空。
- 三个写入口（保存配方 / 映射、导入、按原附件更新）都带各自草稿的基准令牌；同一时间只允许一个整文件写入（`busy`），被拒（`motions_changed`）时面板提示「已被别处更新」并提供「重新读取」。保存完成只把真正写入的那份映射标为已保存（`history.markSavedIf`）。
- 写入顺序：先原子替换文件，再更新索引；索引失败时把旧字节放回（或删掉新文件）再报错。清空时先删文件，再删记录，记录删除失败把文件放回。
- 导入：先筛掉在这副骨架上一个关节都不动的结果（不替换同名旧动作），再按接受项的名字覆盖；提交被拒时说明「附件已加上，动作没保存」。
- 按原附件更新：附件读不出来也留在方案里，同标签下有读不出来的附件时，该片段标为「无法确定来源」保留旧值；重算后不动的结果标为「无可动关节」保留旧值；同 ID / 同名重复的条目不参与循环纠正。导入和更新都显示没对上的部位与躯干参考回退的关节。
- 映射器：胸和颈之间夹一个单链 helper 时，往下穿过它再认颈 / 头（`rigGraph.ts`），只在穿过后确实认出颈或头时才采用；用户映射优先。
- 回归：`tests/unit/library/motions.consistency.test.ts`（替换前失败、替换后索引失败、合法清空、令牌冲突）、`refreshPlan` 组合用例、`retarget.trunk.test.ts` 的 helper / 配方 / 部位用例。

## 12. 发布后复核补丁（0.1.20，2026-10-28 深夜）

依据：一份 0.1.19 发布后的独立复核（未公开）；实验记录在私有仓库。

### 12.1 保存基线是状态，不是步数（lib/history.ts）

- 保存 B → 撤销到 A → 改成 C：新分支丢掉了含 B 的重做，但保存位置还是「第 1 步」，C 恰好也在第 1 步，就被当成已保存（磁盘是 B）。现在提交新步骤时，保存位置若落在被丢掉的重做分支里就失效（-1），C 是未保存。
- 保存在途时撤销：保存完成按「写入的那份映射」在历史里的位置（按对象身份，现在 / 撤销步 / 重做步里找）标为已保存（`markWritten`），找不到就失效；不再要求它仍在屏幕上。这一步在写入函数里做，不放在 onSuccess（面板卸载后 onSuccess 不执行，历史是全局的，回来时要看到正确的保存位置）。
- 面板拿到新文件（首次读取、保存、重新读取）时，历史若干净但映射与文件不同（文件在别处改过），就按文件重新开始；有未保存修改则保留草稿。只在新文件到达时判断，避免「保存刚标记、草稿尚未换成写入文件」的瞬间误判。

### 12.2 重新读取与删除

- 「重新读取」等这次读取返回后一次装入文件、令牌和映射历史；读取失败保留冲突提示并报错，不装入半套。按钮在写入进行中不可用。
- 删除已导入动作：只有写入成功才提示「已删除」（与删除配方一致）。
- 回归：`tests/e2e/motion-recovery.spec.ts`（隔离库真实面板：保存后撤销再改成 C 仍可保存、重做回 B 干净；冲突 → 读取失败保持冲突 → 重新读取装入别处的文件 → 再改再存成功；删除被拒不报成功）；三条在旧实现上都失败。

### 12.3 Unity：状态按它播放的片段命名（插件 0.1.21）

- 0.1.20 的一次性副本用安全文件名，而 Unity 会把原生 `.anim` 的片段名改成文件名：应用里的「Walk?」在 Unity 里变成片段「Walk_」，状态却叫「Walk?」，按片段名找状态的调用（运行时 PlaygroundController、`Animator.Play(clip.name)`）找不到。实测复现后，状态改按它实际播放的片段命名，两者始终同名；只给片段保留应用的名字在新建文件时会被 Unity 改回文件名（实测），不可靠。

### 12.4 瞄准时支撑手在枪上（range/supportArm.ts）

- 有现成瞄准片段时，手臂按片段摆、枪按镜头方向转，支撑手离开枪身：标准 U（2.01 m）水平瞄准 16–18 cm、上仰 29° 约 24 cm、下俯 51° 约 38 cm（真实鼠标、调试接口读骨骼位置）。
- 只修这一只手臂：瞄准中把手移到枪前护木上离它最近的点（沿枪身的位置限制在 25%–75%），上下臂长度不变、肘部留在片段原来那一侧（两骨解析解），按瞄准权重混合。不是全身 IK。修后 −29°～+52° 全程 0–2.5 cm；侧面渲染前后对照见证据目录。
